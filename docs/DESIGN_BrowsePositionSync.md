# 浏览位置跨设备同步：并发冲突与设计方案

> 状态：设计评审（待落地）
> 更新：2026-08-30
> 关联：当前实现见 `ui/panel.html` 的 `scroll_tid`(lww) 与 `read_at`(max)

## 1. 背景：已实现什么

X 客户端的浏览位置同步目前有两套语义：

- `scroll_tid`（策略 `lww`，跨设备）：记录"最后看到的那条推文 tid"，打开面板时把列表滚到该卡片。
- `read_at`（策略 `max`，跨设备）：记录"已读边界"的时间戳，只前进不回退，用于已读置灰。

两者都走 `window.DBoxState`（XSTATE）写服务端、各设备 `pull` 合并。本文只讨论 `scroll_tid`
这类**精确游标**在"单人多端并发"下的冲突，不涉及 `read_at`（它天然单调，不抖）。

## 2. 问题：双设备并发会怎样

你描述的场景：

- 设备 A、B 从同一位置开始。
- A 往上滑看更旧的推文（位置变老）。
- B 往下滑看更新的推文（位置变新）。
- 两端都按滚动持续写 `scroll_tid`。

### 2.1 朴素 LWW（当前到达顺序决胜）的坑

`scroll_tid` 用 last-write-wins：服务端保留"最后到达"的那次写。两端都在滚，写请求交替到达，
服务端游标就在「A 的老位置」和「B 的新位置」之间**来回跳（thrashing）**。任何一端刷新，都可能
定位到一个"不属于自己刚刚在看"的位置。

### 2.2 更隐蔽、更常发生的坑：陈旧写回（stale write-back）

真实世界里一个人不会真的双手同时滚两台设备。但下面这条更致命：

- A 滚到老位置并写盘。
- B 一直挂着没动，它的本地 `scroll_tid` 仍是旧（新）位置。
- B 因重连 / 心跳 / 一次无关写，把**陈旧位置**推回服务端，覆盖掉 A 的最新进度。

根因：写请求的"权威性"按**到达顺序**定，而不是按"谁最近真正在交互"。

## 3. 关键判断：这是"单人多端"，不是"多人协同编辑"

- 协同编辑（Google Docs 多人同时改同一段）= 需无冲突合并 → CRDT / OT。
- 阅读进度（你这个场景）= 同一人的多台设备，**任何时刻只有一台是"正在用"的那台**。

所以目标不是"无冲突合并两个并发位置"，而是：**让"最后真正交互的那台设备"的位置成为权威**，
其余设备要么只读、要么其写不足以推翻权威。这能把抖动概率降到近似零，且实现轻得多。

## 4. 社区成熟方案对比

| 方案 | 思想 | 代表 | 适合本场景？ |
|---|---|---|---|
| **Active-device-wins** | 每台设备存自己的位置；服务端维护"主设备指针 = 最近交互的设备"，恢复时取主设备位置 | Netflix「继续观看」、Pocket/Instapaper 阅读进度、播客单集进度 | ✅ 最贴合 |
| **LWW + 交互时间戳** | 写携带 `deviceId + 交互 ts`；服务端按"最近交互设备"定权威（方案 1 的轻量实现） | 多数阅读/播放类 App 的内部实现 | ✅ 推荐落地 |
| **单调读边界（max）** | 位置只前进不回退 | 已用于本插件 `read_at` 置灰 | ⚠️ 只适合"已读"，不适合精确游标（会丢"往回看"） |
| **向量时钟 / CRDT** | 给每次写打偏序时钟，无冲突合并并发分支 | LWW-Element-Set、G-Set；Google Docs 用 OT/CRDT | ❌ 过度设计（单人场景不需要合并两个真相） |

> 参考实体：Netflix "Continue Watching"（按 profile + 最近播放设备定位）、Pocket/Instapaper
> （最后打开的设备决定阅读进度）、播客 App 的单集进度（最后交互设备）。学术/理论：Lamport
> 逻辑时钟、LWW-Element-Set（CRDT）、Operational Transformation（对比说明协同编辑才需要）。

## 5. 推荐方案：Active-device-wins（LWW + 交互时间戳实现）

### 5.1 数据模型

服务端为每个 `(ns=x, user)` 存：

```
positions: {                          // 每设备各自的位置（互不覆盖）
  <deviceId_A>: { tid, ts },          // ts = 最近一次真实交互时间
  <deviceId_B>: { tid, ts }
}
resume: { tid, deviceId, ts }         // 恢复点 = 最近交互设备的位置
```

### 5.2 写入规则（消除抖动 + 陈旧写回）

- **只在真实用户交互（滚动 / 点击 / 聚焦）时写**，绝不在"加载/重连"时写。
- 每次写携带 `deviceId` 与交互时间戳 `ts = Date.now()`（或更好：服务端接收时刻）。
- 服务端仅在 `新写的 ts > resume.ts` 时更新 `resume`（并把 `deviceId` 记为最新）。
- 即：`resume` 由"最近交互的设备"决定，而非"最后到达的请求"。

效果：

- A 正在滚 → A 的 `ts` 最新 → `resume` 跟随 A，B 的陈旧写（旧 `ts`）被忽略，不会覆盖 A。
- 你放下 A、拿起 B 滚一下 → B 的 `ts` 更新并超过 A → `resume` 切到 B。这是**符合直觉**的切换。
- 两端"同时滚"的极小概率下：`resume` 仍取最近交互者，抖动被约束在"谁最后动"而非"请求到达竞态"。

### 5.3 读取 / 恢复规则

- 打开面板时读 `resume.tid` 定位到上次所在。
- 与现有 `read_at`(max) 分工不变：`read_at` 管"已读置灰"（单调），`resume` 管"精确位置"（最近交互设备）。

### 5.4 可选加固：聚焦即 active

- 监听 `visibilitychange` / 首次滚动：设备变为可见/交互即标记为 active，其写才更新 `resume`；
- 处于后台或被最小化（`DBOX_MODE.hidden`）的设备停止更新 `resume`（只读）。
- 这从机制上保证"同一时刻只有一个设备能改写权威位置"，彻底消除并发抖动。

## 6. 落地要点与陷阱

- **时钟漂移**：不要纯靠客户端时钟比较跨设备 `ts`。优先用**服务端接收时刻**作为 `ts`，或服务端
  对每设备维护单调递增序列。否则两台设备系统时间差会污染"最近交互"判定。
- **离线后回写**：离线时滚了、联网后一次性补写——其 `ts` 是真实最新交互，应胜出（这正是你最后看的）。
  方案天然支持，无需特殊处理。
- **防抖**：滚动批量写（当前 `scheduleSavePos` 已 200ms 防抖）保留，避免每个像素都打服务端。
- **后端改动**：当前 XSTATE 的 `lww` 是按 key 整体"最后写覆盖"，不带 deviceId/交互语义。
  要落地方案 5，需要 XSTATE 后端支持 **per-device 存储 + `resume` 派生**（或插件层保证
  "仅 active 设备写 `scroll_tid`、其余设备只读"——可用 5.4 的聚焦标记在插件侧近似实现，
  无需后端改动，但弱于服务端权威）。

## 7. 结论与建议

- 当前 `scroll_tid` 的 `lww` 实现**在单人单活跃端下基本可用**，真正风险是 2.2 的"陈旧写回"，
  已被"只在交互时写"大幅缓解。
- 若要彻底消除双端抖动与陈旧写回，**推荐落地方案 5（active-device-wins + 交互时间戳）**：
  服务端存 per-device + 派生 `resume`，或至少在插件侧用"聚焦即 active"约束哪台设备能改写权威位置。
- 不推荐为此引入向量时钟 / CRDT——单人阅读场景不需要合并两个并发真相，属于过度设计。

## 8. 修订（采纳）：租约 + Fencing Token

> 2026-08-30 补充：用"服务端签发单调递增租约 ID"取代 5.2 的"客户端交互时间戳"方案。
> 优点：不依赖客户端时钟，彻底消除 §6 的时钟漂移陷阱；同时挡住抖动与陈旧写回。

标准名：**lease（租约）+ fencing token（栅栏令牌）**。参考：Kleppmann《Designing Data-Intensive
Applications》§9 fencing token；同类思想：Raft term、ZooKeeper zxid/generation、K8s resourceVersion。

### 8.1 机制

- 服务端为 `(user, ns=x)` 维护一个**单调递增**的 `leaseId` 与 `leaseOwner`(deviceId)。
- 设备"接管主控权"时调用 acquire：服务端原子自增并返回新 `leaseId`，该设备成为主控。
- 所有写浏览位置的请求携带 `leaseId`；服务端仅当 `携带的 leaseId === 当前最大 leaseId` 才接受，
  否则返回 `{ stale: true }` 拒绝（陈旧设备的写入被"栅栏"挡住）。
- 恢复浏览位置时，读服务端 `scroll_tid`（主控设备的写入结果）。

### 8.2 接口

| 接口 | 语义 | 说明 |
|---|---|---|
| `GET /lease` | peek：只读取当前 `leaseId`，**不接管** | 用于指示灯判断本设备是否已过期 |
| `POST /lease/acquire` | 自增并接管，返回新 `leaseId` | 只在"刻意使用"的时机调用 |

### 8.3 获取时机（关键规则）

- ✅ 绑定在**浏览视图打开 / 刷新 / 面板重新显示**（`openBrowse` → `loadBrowse`、面板 un-hide）上。
  语义是"最后打开浏览页的设备说了算"，可预测。
- ✅ 指示灯上提供**显式「接管」点击**：非主控时点一下即 acquire。
- ❌ **绝不能绑在 scroll 事件上**：否则 A 滚一下抢租约、B 滚一下抢回来，抖动原样复现。
  （这正是"获取 ID 必须和刷新浏览位置的地方绑定，而不是和滚动绑定"的原因。）

### 8.4 指示灯命名建议

统一叫 **「主控」灯**（`authoritative`），两态：

- 🟢 **主控中**：本设备权威，浏览位置会同步到其它设备。
- ⚪ **已让出**：已被其它设备接管，本设备仅本地记忆（不上传）；**点击可接管**。

可选第三态：同步中/连接中（请求在途）。

### 8.5 边界与配套

- **非主控时的体验**：仍写本机 `BROWSE_POS_KEY`（本地刷新照样回到原处），只是不推服务端，
  避免"突然不同步"的困惑。
- **并发 acquire**：服务端必须原子自增（单写者 / 事务），否则两台设备可能拿到同一 ID。
- **离线**：离线期间只写本地；联网后若租约已过期则被拒，指示灯转"已让出"，用户点接管即可。
- **迁移兼容**：无 `leaseId` 的旧客户端按"接受"处理，待其升级后再纳入栅栏。
- 与 `read_at`(max) 的分工不变：置灰走单调边界，不受主控权影响。
