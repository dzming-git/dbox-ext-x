# 首页信息流「海量堆积」浏览方案设计

> 状态：待评审（设计稿）
> 更新：2026-09-04
> 关联：`ui/panel.html` 的 `rebuildBrowseList` / `XFEED.feed('main')` / `saveAnchor` / `restore`
> 关联设计：`DESIGN_BrowsePositionSync.md`（续读锚点 + 主控租约，已实现）

---

## 0. 摘要（给评审者的结论先行）

首页（浏览视图 `view-browse`）目前是 **全量 DOM 渲染**：`rebuildBrowseList` 清空 `brList`
再把所有卡片 `appendChild` 进去，成员上限 `cap:1500`（你计划上调）。

你「一两周才整体读一遍」的痛点其实拆成两件事，必须分开治：

1. **滚动性能**：DOM 里挂 1500+ 张卡片（含图/视频），手机上必然卡、图片逐张撑开布局还会触发锚点恢复的抖动。
2. **定位成本**：打开后要在这条长河里找到「该从哪看起、怎么跳到某天」。

好消息：**「续读到上次位置」已经做好**（`XFEED` 的 anchor + 主控租约，跨设备）。
所以本方案**不需要再发明锚点**，重点是「长列表怎么滚得动、怎么跳得准」。

文档给出 5 个方案（A–E），并推荐**分期组合**：一期做 B+C+D（按天分组 + 已读折叠 + 右侧日期轴），
二期做 A（虚拟滚动）作为 cap 上调后的性能基座。纯分页（E）不推荐作为主方案。

---

## 1. 现状与硬约束（方案必须尊重）

| 项 | 现状 | 对方案的影响 |
|---|---|---|
| 渲染方式 | `rebuildBrowseList` 全量 `appendChild` 到 `brList`（在 `viewBrowse` 滚动容器内） | 无虚拟化；卡片数 = 成员数（≤cap） |
| 成员上限 | `XFEED.feed('main', { cap: 1500 })`，union_by_id 按 `created_at` 倒序封顶 | cap 上调 → DOM 更大 → 必须虚拟化兜底 |
| 排序/时间 | 每卡有 `created_at`，`sortItemsByTime` 按它倒序 | 按天分组零成本 |
| 续读锚点 | `XFEED.anchor()` = 条目 id + 卡内偏移，跨设备、租约门控；`restore()` / `saveAnchor()` 已封装 | 「上次位置」是已有事实，方案直接消费 |
| 已读语义 | `read_at`(max) **已下线**（双向滚动下 max 边界会把几乎整列判成已读，干扰阅读） | 新方案**不得**用「逐条置灰」表达已读，改用「按天折叠」 |
| 无限加载 | 滚到底 `loadBrowse(false)` 按 `brCursor` 拉更旧一页 | 分组/虚拟化不能破坏 `brCursor` 续拉 |
| 内联视频 | 卡片可内联播放 `<video>`；`pull-to-refresh` 已特别处理「给播放中 video 加 transform 会使其重置」 | 虚拟化卸载卡片会杀掉正在播的视频，需专门处理 |
| 运行环境 | 面板跑在 srcdoc iframe，移动端为主 | 方案须对低端机友好，不能纯堆 DOM |

锚点恢复当前依赖「目标卡片已在 DOM 里」（`scrollCardToTop` 用 `offsetTop` 反推 `scrollTop`）。
任何虚拟化方案都要保留这一能力——要么保留真实滚动高度（spacer），要么把虚拟偏移换算成 `scrollTop`。

---

## 2. 评估维度

- **P0 性能**：cap 上调后滚动/恢复是否仍流畅（低端机）。
- **P0 定位**：能否 O(1) 跳到任意一天、回到上次位置。
- **P1 阅读流**：是否保留「刷一遍全局」的连贯感（不强制翻页打断）。
- **P1 与现有机制兼容**：不破坏 anchor / lease / `brCursor` / 内联视频。
- **P2 工作量**：改动面、风险、是否要后端配合。

---

## 3. 方案

### 方案 A：虚拟滚动（Windowing）—— 性能基座

**思想**：只挂载视口内 + 缓冲区的卡片，列表真实高度由占位 spacer 撑出；滚动时回收离屏卡片。

**实现要点**
- `brList` 改为 `position:relative`；每张卡 `position:absolute; transform: translateY(y)`，`y` 来自高度累加表。
- 维护 `heights: Map<tid, number>`：卡片 `ResizeObserver` 回调里更新并触发重排；首屏用估算高度（如 320px），图片/视频 `load` 后校正（这刚好和现有 `watchStableThenAnchor` 的「布局稳定后校正」理念一致）。
- 滚动时算 `[firstVisible, lastVisible]` 区间 → 仅渲染该区间卡片。
- **锚点恢复**：`restore()` 改为「先按高度累加表算出目标 tid 的 `y` → 设 `scrollTop=y-offset`」，无需等卡片挂载；卡片挂载后 `watchStableThenAnchor` 再做一次像素级校正（复用现有管道）。

**风险/代价**
- 内联视频：卸载离屏卡会杀掉播放。对策：① 仅在「无视频在播」时回收视频卡；或 ② 视频卡始终常驻、其余窗口化；或 ③ 滚出视口自动暂停并保留 poster。建议先用 ③。
- 图片：天然变好（离屏图不加载），但需用原生 `loading="lazy"` 或 IntersectionObserver，避免窗口化后批量 load 抖动。
- 工作量最大、回归面最广（触碰渲染与锚点恢复两条核心链路）。

**适用**：cap 真正调到几千+，或全量 DOM 在目标机上已明显卡顿。**建议作为二期**，不在一期强上。

---

### 方案 B：按天分组 + sticky 日期头

**思想**：按 `created_at` 把卡片切成「日」段，每段前插入日期分隔条；滚动时顶部吸住当前日期（sticky）。

**实现要点**
- `rebuildBrowseList` 内排序后，遇 `日` 变化时插入 `<div class="day-sep" data-day="2026-03-12">3月12日 · 周五</div>`。
- `.day-sep { position: sticky; top: 0; z-index: 5 }`（吸顶）。
- 分隔条本身可作为跳转锚点（`scrollCardToTop(daySepFirstTid)`）。

**收益**：视觉不再是一眼望不到头的同质流；随时知道「现在滚到哪天」；给 C/D 提供天然挂载点。
**代价**：不减少 DOM 数（cap 大时仍卡）→ 必须与 A 或 C 配合才有真实收益。
**工作量**：小（纯渲染层改动，不碰锚点/加载）。

---

### 方案 C：已读折叠（按锚点派生「已看天」，非置灰）

**思想**：复用已有锚点定义「看过哪」。锚点 = 上次看到的 tid；其所在「日」及**更旧**的所有日 = 已看 → 折叠成细条（`3/12 · 40 条 · 展开`）；锚点**更新**日及**更新**的所有日 = 未看 → 展开。

> 关键区分：这里**不是** `read_at` 的逐条置灰（已下线），而是「按天折叠」——
> 已看的天收成一条，点一下才展开。和「时间线双向滚动」不冲突，不会整列变灰。

**行为刻画（契合你「一两周读一遍」）**
- 你每周打开：锚点停在上一周的位置 → 上一周及更旧 = 已看 = 折叠；这一周新进来的 = 未看 = 展开。
  → 打开即只面对「新增量」，滚动量从全表骤降到「一周增量」。
- 本次会话往下滚读：锚点随阅读下移，滚过的天逐个翻成「已看」→ 身后自动收起，列表越读越短。
- 首次大清理（很久没看，pile 很大）：当次仍需滚完整个 pile（折叠主要收益在**会话之间**，不在首次 catch-up）；首次 catch-up 的顺滑靠 A + D。

**实现要点**
- 保留 `dayIndex: Map<day, {firstTid, count, topOffset}>`（B 已产出，复用）。
- 锚点变化（`saveAnchor`/`restore`）时重算各天折叠态；折叠态只控制「该天卡片容器 `display` + 分隔条文案」，内容 DOM 仍在（轻量）；若 cap 很大，可进一步配合 A 把折叠天彻底不挂载。

**收益**：直击「堆积」的本质——跨会话把已读 pile 收起来，只留新东西。
**代价**：依赖锚点准确性（已可靠）；和 `read_at` 语义无关，无回归。
**工作量**：小–中（与 B 共用 dayIndex，主要加折叠态管理 + 点击展开）。

---

### 方案 D：右侧日期轴 / 时间轴导航（密度条 + 跳转）

**思想**：右侧常驻一条「日期轴」：每格 = 一天，高度/色深反映当天堆积密度（条数），高亮当前天；点击 → 跳到那天。

**实现要点**
- 由 `dayIndex` 渲染右轴 `dayRail`；每次 `rebuildBrowseList`/锚点变化重算密度与高亮。
- 点击某天 → `scrollCardToTop(dayIndex.get(day).firstTid)`（或虚拟偏移，若已上 A）。
- 滚动时 `IntersectionObserver`/scroll 节流更新「当前天」高亮（和现有 `brScroll` 节流同源，不新增通道）。
- 手机端：右轴默认收起，点「轴」按钮浮出；或吸附在右侧极窄（4–6px 密度条），长按展开。

**收益**：你提的「右侧时间轴」想法。本质是 B/C 的**快速导航层**——既是跳转入口，也是折叠开关（点轴上某天 = 展开/收起那天）。O(1) 跳到任意一天，彻底告别手动滚几千 px。
**代价**：UI 空间占用（窄屏需折叠态）；与 B 强耦合（天数据来自 B）。
**工作量**：小–中。

---

### 方案 E：纯分页（翻页）

**思想**：把列表切成固定页（如每页 50），只渲染当前页，prev/next 翻页。

**不推荐作主方案**
- 破坏「刷一遍全局」的连贯感（你本就是要通读），翻页是打断。
- 与无限滚动 `brCursor`、锚点续读哲学冲突（锚点是「条目级」，分页是「页级」，跨页续读要额外映射）。
- 定位能力弱于 D（D 能跳任意天，分页只能相邻跳）。
- **仅可作**：极端低端机、且 A 暂未上的临时降级态（每页少卡保流畅），不作为目标形态。

## 4. 推荐组合与分期

```
性能基座(A)  ──┐
              ├── 持久形态（cap 上调后也必须顺）
按天分组(B)  ──┤
已读折叠(C)  ──┤   ← 直击「堆积」：跨会话只留新增量
右侧日期轴(D)──┘
```

**一期（性价比最高，不动渲染内核）**：**B + C + D**
- 不碰 `rebuildBrowseList` 的挂载方式，只在其上叠「分组/折叠/导航」。
- 锚点续读已就绪 → C 直接复用，把「已读 pile」在会话间收起，你打开只面对新增量。
- D 让「首次大清理」也能一键跳到某天，不必手动滚。
- cap 即便上调到几千，由于 C 把已看天收成细条、**D 让你跳着读**，DOM 与滚动量都可控；只有「单天展开 + 真·长列表滚动」才需 A 兜底。

**二期（cap 真上调到几千+，或目标机已卡）**：引入 **A 虚拟滚动**
- 与 B/C/D 正交：B 的分组头、C 的折叠态、D 的轴都建立在「有 dayIndex + 真实滚动高度」之上，A 只把「全量挂载」换成「窗口化挂载」，接口不变。
- 上线顺序建议：先 B → 验证分组/吸顶 → 再 C → 再 D → 最后 A。每步可独立验证、独立提交。

**必不做**：E 作为主形态。

---

## 5. 风险与待评审问题

1. **cap 上调幅度**：你计划调大到多少？若 ≤3000，一期 B+C+D 足够；若 5000+，A 应提前。
2. **「已看」定义**：C 用锚点派生（锚点及更旧 = 已看）。是否接受「没真正滚到、只是锚点在其后」也算已看？
   替代：显式「标记本周已读」按钮，或按「距今天数」折叠（如 ≥7 天自动收起）。
3. **内联视频 + 虚拟化（二期 A）**：卸载杀播放的问题，倾向「滚出自动暂停 + 保留 poster」还是「视频卡常驻不回收」？
4. **右轴在手机端形态**：常驻窄密度条（4–6px）还是按需浮出？需你定。
5. **与 `read_at` 的关系**：确认 C 的折叠**不**复用 `read_at`，仅用锚点 + 天数，避免复活已下线的置灰逻辑。
6. **锚点恢复在折叠下的行为**：C 折叠后目标卡在「收起的天」里，恢复时需先展开那天再定位（点展开 → `restore`）。

## 6. 落地建议（若评审通过）

按 B → C → D → A 顺序，每步独立提交、Edge 截图验证：
- B：分组头 + 吸顶，截图确认分段与吸顶。
- C：锚点派生折叠，截图确认「打开只展新增量、滚过自动收起」。
- D：右轴密度 + 点击跳转，截图确认跳转与高亮。
- A（二期）：窗口化 + 高度表 + 锚点换算，截图确认长列表滚动帧率与恢复精度。

> 文档基于 `ui/panel.html` 现状（`rebuildBrowseList` 全量挂载、`XFEED.feed('main')` cap:1500、锚点/租约已实现、`read_at` 已下线）。
> 所有方案均复用现有 `created_at` 排序与锚点机制，无后端改动（A/B/C/D 纯前端）。
