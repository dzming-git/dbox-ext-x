# 多关键词搜索：缓存隔离与结果融合方案

> 状态：已实现，**待端到端验证**（测试环境登录失效，仅做语法校验与算法仿真）
> 更新：2026-09-02
> 关联：实现见 `ui/panel.html` 搜索段；缓存键 `search:kwlist` / `search:kw:<key>`；
> 锚点键 `feed:search:<key>:anchor`、`feed:search:__all__:<Top|Latest>:anchor`

## 1. 需求

用户要同时跟踪多个关键词，且：

1. 每个关键词**独立缓存**；
2. 可随时增删关键词，**增删时其他关键词的缓存不重置**；
3. 支持单个关键词重新搜索（放弃缓存重爬），也支持全部重新搜索；
4. **融合显示是主功能**——所有关键词的结果合成一条流；单个关键词查看只是锦上添花。

第 4 条是最容易被误解的一条：**"独立管理"不等于"独立显示"**。缓存要隔离，
呈现要合并。这两件事在数据层是相反的方向，实现上必须显式分开处理。

后端 `/search` 本就按 `q` 参数化、自身不带缓存，因此本次**只改前端**。

## 2. 数据布局：每关键词一个独立键

| 键 | 策略 | 内容 |
| --- | --- | --- |
| `search:kwlist` | lww | 关键词清单 `[{q, key, added_at}]` + 当前查看的 key |
| `search:kw:<key>` | lww | 该词 Top/Latest 两套结果 + 游标 + 时间戳 + 错误 |
| `feed:search:<key>:anchor` | lww | 该词的浏览位置（框架 `feed()` 管理） |
| `feed:search:__all__:<模式>:anchor` | lww | 融合视图的浏览位置（按模式分开记） |

**为什么不用一个大对象存全部关键词**：lww 是整值覆盖。若所有关键词挤在
`search:all` 一个键里，设备 A 更新词 1、设备 B 更新词 2，后到达的那次写会把前者
**整包盖掉**；删除一个词也要重写整包。独立键使每个词的写操作互不影响，这才是
"增删关键词时旧缓存不重置"的实现基础。

删除关键词时只从清单摘除、并清掉内存副本，**服务端 `search:kw:<key>` 原样保留**。
于是误删后再加回同一个词，旧结果立刻回来——否则"移除"就变成了"清空历史"，
对一个随手点的 ✕ 来说惩罚太重。

`key` 由 `kwKey(q)` 生成：小写归一 + 连续空白折叠 + djb2 短哈希。

- 归一化是必要的：否则「AI art」和「AI  art」（多敲一个空格）会变成两个关键词、
  各存一份缓存，用户看着像凭空多出一个重复项。
- `#` 与 `@` **不**折叠：X 里它们是话题与用户句柄，语义不同。
- 显示始终用用户输入的原文，key 只用于寻址。

## 3. 融合排序

融合视图（`ALL_KEY = '__all__'`）把所有关键词在当前模式下的结果合成一条流，
跨关键词按 `tweet_id` 去重（几个词很容易搜到同一条推文），保留排序中先出现的那份，
它带的 `kw` 就是这条的来源标签。

### 3.1 最新模式：时间倒序

时间戳跨关键词天然可比，直接 `sortItemsByTime()`，不需要额外设计。

### 3.2 热门模式：组内保序 + 组间择优归并

每个词的 Top 列表是 X 自己算的「相关性 + 热度 + 时效」综合序，**组内顺序本身就有
信息量**，不应被我们按互动数重排。理由有二：

1. **会丢信息**：X 的排序含相关性与作者权威度，这些不在互动数里。搜「苹果」时
   X 会优先放官方账号，纯互动数排序可能把营销号顶上来。
2. **量级不可比**：爆款词动辄上万赞，冷门词几百赞。一比绝对互动数，冷门词就
   永远沉底——那还不如直接看单个词，融合就失去意义了。

所以做法是 **k 路归并**：每个词是一个已排序队列，每次从各队队首挑最该露面的出队。

```
出队分 = 位置分 × 新鲜度
位置分 = (1 + 该词已出队条数) ^ -0.7
新鲜度 = (1 + 年龄小时 / 48) ^ -0.5
```

- **位置分**让"刚出过一条的词"自动让位 → 各词自然轮流露面，不会被某个高频词刷屏。
- **新鲜度**让老内容适度让位给新内容。

#### 参数是实测调出来的，不是拍的

最初用线性版本 `位置分 = 1/(1+0.15n)`、`新鲜度 = 1/(1+age/48)`，仿真结果退化成了
**「按词分块」**——内容普遍较老的词整个沉到底部：

```
A = 10 条(1 小时前)  B = 10 条(72 小时前)  C = 3 条(1 小时前)

线性：CAACACAAAAAAABBBBBBBBBB     ← B 整块沉底
现在：ACBACACBAABAABAABABBBBB     ← 三词交错
```

两个原因叠加：

- 线性位置分衰减**太慢**：要让 A 的位置分降到与 B 同档，A 得先出满 10 条；
- 线性新鲜度又**太陡**：1h → 0.98、72h → 0.40，相差 2.45 倍。两者一乘，
  实际效果等于"先按词的新旧排序，再按词内顺序输出"。

改成幂律 + 平方根后，72h 的新鲜度是 0.63，只做调剂、不做判决。极端新旧差
（2h / 300h / 600h）下的仿真：

```
AAABAAACBBCBCBBCCC     ← 新的略先，旧的也不埋没
```

**验证方式**：从 `panel.html` 里正则提取 `mergeTopQueues` 源码，用 `new Function`
构造后跑仿真——验证的是文件里的真实代码，而不是手写副本（副本会与实现漂移）。
排序这类"参数决定观感"的逻辑，必须能一键重跑验证，否则后续无人敢调参。

## 4. 翻页与浏览位置

- **单词视图**：沿用原有逻辑，按该词当前模式的游标翻页，追加渲染。
- **融合视图**：翻页进度分散在各关键词的游标上，不存在单一游标。做法是让
  **所有还有游标的词并发各翻一页** → 重算融合 → 整体重渲染。
  不能只往末尾追加：融合是全局排序，新条目可能插在中间，追加会让顺序失真。
  整体重渲染后，用 `feed.capture()` / `restore(anchor)` + `cancelRestore()`
  把视口拉回用户正在看的那条（只保留首次定位，取消框架那套固定延时的多次补偿——
  内容刚变长时，补偿定位会落在不同的布局快照上，反而制造跳动）。

融合视图的锚点**按模式分开记**（`search:__all__:Top` / `:Latest`）：两种模式的
内容与顺序都不同，共用一个锚点会互相顶。

## 5. 交互

```
[输入关键词，回车添加并搜索…] [＋ 添加]
(●) 全部  23    ( ) 风景照 42 ⟳ ✕   ( ) AI 绘画 18 ⟳ ✕
点关键词切换查看 · ⟳ 单独重搜 · ✕ 移除（缓存保留）   [⟳ 全部重搜]
```

- **「全部」chip 固定排最前且是默认视图**：打开搜索页、URL 不带 `?q=` 都落在融合流。
- 点关键词 = 只看该词（锦上添花）；⟳ = 该词放弃缓存重爬；✕ = 移出清单，缓存保留。
- **「全部重搜」串行逐个重爬**：并发容易触发 X 反爬（令牌/限流），且串行能显示
  `重搜 2/5` 的进度。
- **绝不自动搜索**：打开视图、从 URL 带 `?q=` 进来，都只渲染已缓存内容或把词填进
  输入框，只有「＋添加」和 ⟳ 才打网络。否则一进面板就替用户爬一堆关键词。
- 融合视图中每张卡片标出来源关键词（`.kw-src`），否则混排后用户看不出它为什么出现。

## 7. 遗留可选项

- **排序参数可调**：0.7（轮转速度）、48（新鲜度半衰期小时）目前是硬编码的仿真
  最优值。若真实数据下觉得"轮得太碎"或"老的太多"，改这两个数即可重跑仿真验证。
- **融合视图的翻页粒度**：现在是"所有词各翻一页"，若某个词内容特别多，可以考虑
  改成"挑缓存最少的词补页"，让各词进度更均衡。
- **后端补图片尺寸**：X 列表接口不返回图片尺寸，前端只能预探测（见 2026-09-02
  另一节）。彻底方案是后端收录时把宽高写进缓存。
